# Supplier admission application

The business lives in `server/srm/`, `server/routes/srm.ts` and `client/pages/srm/`. Native email/password registration is enabled; email verification and password recovery delivery are deferred by the user. Referrer text is a plain user field copied into the first company draft; it never resolves to an internal account or grants access.

Approval owns review tasks and conclusions. `srmCompanies` is the lifecycle record, with separate editable draft and immutable submitted snapshot. One non-claimable procurement pool decides on its first authorized answer. Rejection leads to the editable rejected state; resubmission creates a fresh run and version. Snapshot and audit writes share the lifecycle transaction. Never write a lifecycle status directly.

The `srm-procurement` role is initialized by a seed and assigned explicitly through User management. Root administration alone does not qualify someone to approve. Page and business grants are separate. Every decision rechecks current role membership and active identity. New managers participate in new submissions; existing stays retain planned candidates. Removing a manager prevents their old tasks from being handled; retain at least one current candidate until pending applications are processed. This MVP has no transfer or delegation.

Qualifications use File Repository and private local Drive. Content streams through authenticated application routes. Reviewers can read files referenced by submitted versions; draft uploads remain owner-only. Removing a draft attachment never deletes bytes or historical references. Notification effects use immutable submission snapshots and the originating approval run. Their results retain the native Notification ID, so workflow management can inspect delivery status and retry failed deliveries separately from a failed effect.

`pnpm nocobase db sample` loads optional, repeatable fictional users, categories, PDFs and four business states after validation. It grants no wildcard business role. See `docs/srm-testing.md` for sample accounts and cleanup boundaries. Do not load these samples into a customer production database.

This standalone application uses published npm packages only. Keep its package identity, source extensions and route override registration in `client/runtime.ts`. Do not copy workspace/catalog references, source-checkout Vitest inlining, local configuration or generated collections from the original demo. Regenerate collections with the application CLI.

`server/app.ts` registers a scoped observer before native Users routes because a business provider starts after route registration becomes immutable. It records confirmed user-role assignment differences, operator identity and result, without reading or logging passwords. Native Users remains responsible for authorization, transactions and idempotency. Keep this observer when upgrading the application entry.

Public onboarding lives at `/supplier`; `/login` is the supplier entry and `/login?portal=staff` is the employee entry. Both use native authentication and the same users. Entry selection never grants a role. Only successful native public email registration receives `srm-supplier`; internal accounts are provisioned through Users. If account creation succeeds but supplier assignment fails, the request fails closed and the localized registration recovery hint directs the person to sign in and ask an administrator to assign Supplier applicant through User management. Do not retry registration as recovery.

The `applyAdmission` business action requires an explicit effective grant, even for root. Own profile, submission, upload and owner-file reads require it; ownership alone does not retain revoked access. The one-time supplier-access seed preserves existing company owners, leaving unrelated users unchanged. Users and Roles remain the management surfaces. The shell composes `useSupplierNavigation` because generic page authorization treats root as unrestricted, while supplier identity must remain explicit; preserve this additional menu filter on template upgrades. The home dashboard filters supplier and internal work independently, so dual-authorized accounts can reach both without switching credentials. Approval's native applicant exclusion and the business decision endpoint prohibit self-review.

Supplier admission uses one submission action below the declaration at the end of the form, as requested by the user (page-specific replacement for the L2 header-action default). There is no manual draft-save action. Validate the current profile before confirmation, display localized field-specific correction guidance, then persist the profile and submit with the returned lifecycle version. The existing draft API remains the internal persistence step; a failed save must never send a submission request. Keep footer placement, first submission, rejected-profile resubmission, and validation recovery covered by the admission page tests.

The source demo used unreleased `ListState` helpers. `client/lib/list-state.ts` retains that behavior using published APIs; replace it only when a compatible published client exports the helpers. Test setup registers the TypeScript loader for native database seed imports outside Vite. The migration test resolves Authentication migrations from its published `dist/database` directory. Keep jsdom pinned while Vitest's multipart adapter depends on its Blob internals.
